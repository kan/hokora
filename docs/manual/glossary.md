# 用語集

hokora の文書、画面、コマンドに出てくる言葉をまとめます。

コード、API、監査ログは英語の用語を使い、Web UI は日本語のラベルを表示します。
英語と日本語で呼び名が違うものは、両方を載せています。

| 文書 / コード / API | Web UI の表示 |

## secret の階層

### secret

hokora が預かる秘匿情報の値です。
DB のパスワード、API トークンなどを指します。
値は「有効な UTF-8 で、NUL バイトを含まず、64 KB 以下」である必要があります。

### project（プロジェクト）

secret をまとめる一番上の単位です。
アプリやサービスごとに作ります。
slug で識別します。

### environment（環境）

project の下の単位です。
`prod`、`staging` のように、同じアプリの実行環境ごとに作ります。
アクセス権は環境の単位で割り当てます。

### item

環境の中の 1 個の secret です。
key と値の組で、値には版があります。

### key

item の名前です。
`DATABASE_URL` のように、大文字の英字、数字、アンダースコアで書きます（先頭は英字かアンダースコア、128 文字まで）。
`hokora-client run` が環境変数名としてそのまま使うため、この文字種に限っています。

### slug

project と environment の識別子です。
小文字の英字、数字、ハイフンで書きます（先頭は英字か数字、64 文字まで）。
URL にそのまま載ります。

### version（版）

item の値の世代です。
同じ key に値を保存し直すと、上書きではなく新しい版が足されます。
過去の版は履歴の画面で確かめられます。
アプリが取得するのは常に最新の版です。

## マシンとアクセス権

### machine（マシン）

secret を取得する側の単位です。
Web アプリ、バッチなど、1 つのシステムにつき 1 個作ります。
マシンは 1 個の credential を持ちます。

名前に反して、物理的なホスト 1 台を指す言葉ではありません。
脅威モデルと設計文書が「アプリサーバー」と呼ぶのは、アプリが動いているホストのことで、マシンとは別の概念です。

### credential

マシンの認証情報です。
`HOKORA_CLIENT_ID` と `HOKORA_CLIENT_SECRET` の組です。

- どちらもサーバーが生成します。
  人が値を決めることはできません
- `HOKORA_CLIENT_SECRET` は、作成時と再発行時に 1 回だけ表示されます。
  後から見直すことはできません。
  失ったら再発行します
- サーバーは `HOKORA_CLIENT_SECRET` のハッシュだけを保存します

### grant（アクセス権）

マシンが「どの環境の secret を取得できるか」の割り当てです。
マシンと環境の組で 1 個です。
アクセス権のある環境の item は、全て取得できます。
key ごとの割り当てはありません。

### token（トークン）

マシンが credential で認証すると受け取る、短命の通行証です。
有効期限は 15 分で、延長はできません。
SDK と `hokora-client` が内部で扱うので、利用者が直接触ることはありません。

トークンは「認証が済んだ」ことの証明で、「取得してよい」ことの証明ではありません。
サーバーは secret を返すたびに、マシンが無効化されていないか、アクセス権が残っているかを確かめ直します。

### revoke

マシンの無効化、credential の再発行、アクセス権の削除をまとめた呼び方です。
**止まるのは、それ以降の取得だけです。**
既に取得された secret は相手の手元に残ります。

## 人のユーザー

### user（ユーザー）

Web UI にログインする人です。
ロールは admin の 1 種類だけで、全てのユーザーが全ての操作をできます。

### session（セッション）

Web UI のログイン状態です。
ログインから 12 時間、または最後の操作から 2 時間で切れます。
パスワードを変更するか、ユーザーが無効化されると、そのユーザーのセッションは全て消えます。

## 鍵と暗号

### マスターキー（MK）

暗号の一番上の鍵です。
`hokora init` が 1 回だけ出力します。
**hokora は MK をディスクに書かず、再表示もできません。**
人がパスワードマネージャで保管します。
MK を失うと、保存した secret は復号できなくなります。

### KEK

MK から導出する鍵です。
unseal のときだけメモリ上に作り、DEK を復号したらすぐ消します。

### DEK

secret の値を暗号化する鍵です。
DB には KEK で暗号化した状態で入っています。
unsealed の間だけ、復号した DEK がサーバーのメモリにあります。

### envelope encryption

「MK で KEK を作り、KEK で DEK を守り、DEK で secret を暗号化する」という、鍵を段にする方式です。
MK を替えても（`rotate-master`）、secret を暗号化し直さずに済みます。

### seal / unseal、sealed / unsealed

サーバーの 2 つの状態と、その切り替えです。

| 状態 | 意味 |
|---|---|
| sealed | DEK がメモリに無い状態。secret の読み書きはできません。起動直後は必ずこの状態です |
| unsealed | DEK がメモリにある状態。通常の運用はこの状態で行います |

unseal は、MK を渡して sealed から unsealed へ切り替える操作です。
seal はその逆で、DEK をメモリから消し、発行済みのトークンを全て無効にします。
seal は緊急時の遮断にも使います。

sealed の間も、Web UI へのログイン、パスワードの変更、unseal はできます。

### reveal（表示）

Web UI で secret の平文を見る操作です。
一覧では値を常に伏せてあり（サーバーが値を返しません）、「表示」を押したときだけ平文が出ます。
「表示」を押した操作は、1 回ごとに監査ログへ記録されます。

## 接続先

### Web UI

人が操作する画面です。
VPN の内側からだけ届く場所に置きます。

### Machine API

アプリが secret を取得する HTTP API です。
SDK と `hokora-client` がこれを呼びます。

### admin socket

サーバー上の Unix ソケットです。
`hokora unseal`、`seal`、`status`、`rotate-master` がこれを使います。
サーバーに入れる管理者だけが届きます。

### SDK

Go のアプリに組み込むクライアントライブラリです（`github.com/kan/hokora/sdk`）。
secret をメモリ上の `[]byte` で受け取ります。

### hokora-client

アプリサーバーに置く、取得専用のコマンドです。
サーバー本体の `hokora` とは別のバイナリです。
Go 以外のアプリや、SDK を組み込めない既存のアプリで使います。

### bulk fetch

アクセス権のある環境の secret を、1 回の呼び出しで全て取得することです。
SDK の `Fetch`、`hokora-client bulk`、`hokora-client run` がこれに当たります。
監査ログには key ごとに 1 行が残ります。

## 監査

### 監査ログ

誰が、いつ、何をしたかの記録です。
secret の読み取りは、失敗したものも含めて全て残ります。
secret の値そのものは記録しません。

### actor（実行者）

操作をした主体です。
ユーザーかマシンです。
存在しない client_id やユーザー名での認証の失敗は、`anonymous` と記録します。

### action（操作）

操作の種類です。
`secret.read`、`secret.reveal`、`machine.create`、`grant.delete` のように書きます。
一覧は [設計文書](../DESIGN.md) の §5.4 にあります。

### result（結果）の `success`

`secret.read` の `success` は「secret の送信を始めた」という意味です。
相手が確かに受け取ったことまでは示しません。
侵害の調査では「漏れたかもしれない」記録として扱います。

### 刈り込み（`hokora audit-prune`）

古い監査ログを消す操作です。
hokora は自動では監査ログを消しません。
消えるのは、指定した期間より古い「マシンの読み取りの成功」と「マシンの認証の成功」の行だけです。
失敗の行と人の操作の行は残ります。

### fail closed / fail open

監査ログへの記録が失敗したとき、操作をどうするかの方針です。

| 方針 | 意味 | 当てはまる操作 |
|---|---|---|
| fail closed | 記録できなければ、操作を拒否する | secret の読み書き、認証、unseal、作成の操作 |
| fail open | 記録できなくても、操作は通す | seal、マシンやユーザーの無効化、アクセス権の削除、credential の再発行、パスワードの変更、ログアウト |

fail open にしているのは、安全側に倒す操作です。
監査ログの障害で緊急の遮断が止まらないようにするためです。

## 削除と無効化

### 論理削除

project、environment、item の削除は、行を消さずに「削除済み」の印を付けます。
削除したものは画面に出なくなり、アプリからも取得できなくなります。
削除した slug と key は、新しく作るときに再び使えます。

### 無効化（disable）

ユーザーとマシンには削除がなく、無効化だけがあります。
無効化した後も、監査ログの実行者として参照され続けるためです。
無効化したユーザー名と client_id は、再び使えません。

## 脅威モデルの言葉

### secret zero problem

「secret を守る仕組みに入るための最初の秘密を、どこに置くか」という問題です。
hokora では credential がこれに当たります。
アプリと同じ OS ユーザーの権限を取った攻撃者は credential を読めるので、そのマシンに割り当てた secret も取得できます。
hokora はこの問題を解きません。

### T1 から T4、N1 から N8

脅威モデルが付けている番号です。
T は想定する攻撃者、N は想定しない攻撃者です。
定義は [脅威モデル](../THREAT_MODEL.md) の §3 と §4 にあります。

### レート制限

認証の回数の上限です。
送信元 IP ごとに 1 分 30 回、credential ごとに 1 分 10 回（既定）です。
credential ごとの上限は、マシンごとに 10 から 30 の範囲で変えられます。
